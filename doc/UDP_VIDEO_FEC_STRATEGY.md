# UDP 视频 FEC 策略（分段规则 + 可交织发包）

> 目标：在不依赖额外控制面字段的前提下，让 UDP 视频链路在“连续丢 2 个包”的典型 burst loss 下仍具备较高的恢复概率；同时保证策略可实现、可推断、低 CPU/低 GC，并将冗余控制在可接受范围（例如 ≤40%）。
>
> 本文档**只定义 FEC 编码/分组/发包顺序的规则**；不绑定具体 UDP 头部字段。你们可以用现有的 `FragmentIndex/TotalFragments` 承载，也可以未来升级为 HeaderV2（TableId/ProfileId），但策略本身不变。

---

## 1. 术语与约束

- **源分片数**：`N = TotalFragments`（一帧原始视频分片数量）。
- **符号（symbol）大小**：每个分片的 payload 上限为 1200 字节；最后一个分片可能小于 1200。
- **组（Group）**：一次 FEC 保护的基本单位。
  - 组参数记为 `(K, R)`：每组 `K` 个源包，生成 `R` 个 parity 包。
  - 该组最多可恢复 `R` 个组内丢失（在 RS/Cauchy 等线性码下）。
- **核心鲁棒性要求**：必须支持 **R≥2** 的工作模式，否则“连丢 2 个包”在数学上无法恢复。

本文默认：
- 所有源包（原始分片）只发送一次。
- FEC 分组只用于生成 parity；不会为了“让分组好看”而重复发送源包。

---

## 2. 总体思想（必须能跳起来）

你们的关键经验是：网络/系统经常出现 burst drop（连续丢包），而传统“顺序发 0..N-1”会让 burst 丢失集中命中相邻分片（尤其帧尾）。

因此本策略由两部分共同完成：

1) **组内纠错能力**：使用 RS 类短块码（例如 Cauchy RS），确保每个保护单元 `R≥2`。

2) **发包交织（Interleave）**：无论 `N` 是多少，都必须能构造一个“跳得起来”的发送顺序，把 burst loss 尽量打散。

> 注意：交织是“发包顺序”的置换，不改变 `FragmentIndex` 的编号含义。

---

## 3. 全量查表策略（4 ≤ N ≤ 255）

**V2.0 策略核心变更**：
1.  **覆盖范围**：从 N=64 扩展至 N=255，适应单眼 4K/VR 高清帧。
2.  **ID扩展**：`FecProfileId` 使用 16 位（2字节）。
3.  **大包策略**：利用大 N 的自然离散优势，允许 `16 ≤ K ≤ 32`，优先保证冗余度贴近 25%。
4.  **抗突发**：大组数（Stride）优先。随着 N 增大，Stride 自动增大，抗 Burst 能力增强。
5.  **小包保护**：N < 8 不保护（VR 保证不出现极小帧，或由 TCP/WS 负责控制信令）。

### 3.2 查表说明与 ID 计算

- **交织算法**：对于表中指定的 G (组数)，源包 `i` 属于组 `g = i % G`。
- **ID 隐式推断**：
  - 接收端根据 N 查表得到 TotalParity 和 GroupConfig。
  - 收到 Index >= N 的包，即为 Parity 包。
  - `ParityOffset = Index - N`。
  - `GroupIndex = ParityOffset % Groups`（假设 Parity 也是交织发送）。
  - 该包为该组的第 `ParityOffset / Groups` 个冗余包。
- **无填充**：K 值根据 `N % Groups` 自动分配，无需 Padding。

---

## 4. 大 N (≥ 256) 策略建议

若偶发 N >= 256，建议：
1. **Groups** = `Ceiling(N / 32)`。
2. **R** = 8。
3. **Stride** = Groups。
4. **尾部**：无需特殊处理，K 值自动分配。

---

## 4. 交织发包：用“矩阵转置”保证能跳起来

这里的“步长”采用你们更直观的定义：

- 当组大小为 `K` 时，令 `G = floor(N / K)`（从头能凑出的完整组数）。
- 交织发送源包时，相当于用 `G` 作为“跨组步长”（按列发送）。

### 4.1 源包交织（不重复发送源包）

对“从头分块的完整部分”做交织：

1) 令 `K` 为当前段使用的基础组大小（8/16/32）。
2) 令 `G = floor(N / K)`。
3) 把源包 `0..(G*K-1)` 视作 `G x K` 的矩阵，按行填充：
   - 第 g 行第 i 列：`idx = g*K + i`
4) 发送时按列优先（矩阵转置）：
   - for i in 0..K-1:
       for g in 0..G-1:
           发送源包 idx = g*K + i

这样相邻发送的源包来自不同组，能有效打散 burst loss。

对“尾包剩余部分”（`N - G*K` 个源包），不强行塞进上述矩阵；它们的保护由第 3 节中显式的“尾组”（8/16/32）负责。

### 4.2 parity 的发送顺序（建议）

- parity 同样建议按“组间交织”发送：不要把某一组的 parity 一次性发完。
- 推荐顺序：先源包交织，再 parity 交织。

## 6. 无 FecGroupId/FecGroupIndex 的可推断编码布局（建议）

你们希望 `FecGroupId/FecGroupIndex` 不是必要字段，只要规则固定即可推断。

这里给出一种**完全可推断**且与交织发送相容的布局建议：

### 6.1 包编号（逻辑编号 != 发送顺序）

- 源包使用 `FragmentIndex = 0..N-1`。
- parity 包依次编号：
  - `FragmentIndex = N .. N+P-1`（按组、按 parity 序号固定顺序排列；P 为本帧 parity 总数，包含尾组产生的 parity）。

> 发送端可以按第 4/5 节交织发送，但 `FragmentIndex` 的值不变。

### 6.2 parity 的固定排列

对每一种组类型 `(K,R)`：

- parity 生成顺序固定为：先组号递增，再 parity 序号递增。
- 尾组（`N-8..N-1` 或 `N-16..N-1` 或 `N-32..N-1`）视作“最后一个组”，其 parity 放在该帧 parity 段的末尾。

接收端只要知道 N 以及第 3 节的分段规则，就能唯一重建每个 parity 对应的源包集合。

---

## 7. 落地注意事项（避免极端情况）

- 冗余上限：若某些分段组合导致冗余 > 40%，允许对“尾组”的 parity 做降级（例如尾组原本 `(16,4)` 可降为 `(8,2)`），但尽量保持 `R≥2`。
- 小帧极端：`N<4` 不做冗余；`N<3` 时系统只能尽力。
- 交织与实时性：交织不应引入额外缓存等待；应在“本帧包已准备好发送”后立即计算交织顺序并发送。

---

## 8. 与静态表（TableId/ProfileId）的关系

如果采用静态表（推荐），则文档中的 `(32,8)/(16,4)/(8,2)` 对应为不同的 `FecProfileId`。

- `FecProfileId` 只决定编码矩阵/系数规则。
- 分段选择与交织规则属于“上层策略”，仍按本文档执行。

## 9. 示例（说明发包顺序与编号分离）

假设某帧 `N=20`：落在 `16 ≤ N < 32`，使用 `(8,2)`。

- 基础组：`0..7`, `8..15`
- 尾组：`12..19`

逻辑编号（FragmentIndex）会是：
- 源：0..19
- parity：20..(20+P-1)（P 为所有组 parity 总数）

发送顺序：
- 源包对 `0..15` 做 `G=2, K=8` 的矩阵转置交织发送：`0,8,1,9,2,10,...,7,15`
- 余下源包 `16..19` 按实时性直接发送（它们会被“尾组”保护）
- parity 按组间交织发送
